# Иерархическая структура работ проекта поиска рецептов

Теги обозначают согласованные роли исполнителей. Задачи внутри модуля выполняются параллельно там, где это возможно.

## 1. Управление проектом
### 1.1. Запуск и планирование
- 1.1.1. [PM] Подготовить устав проекта: цель, границы, критерии приёмки и ограничения.
- 1.1.2. [Вся команда] Согласовать состав модулей, результаты и оценки задач ИСР.
- 1.1.3. [PM] Составить зависимости задач, PERT-оценки и календарный план.
- 1.1.4. [Вся команда] Подтвердить распределение ролей и доступное время каждого участника.
### 1.2. Оперативное управление в каждом спринте
- 1.2.1. [PM] Проводить планирование, короткие встречи, обзор результата и ретроспективу.
- 1.2.2. [Вся команда] Обновлять статус задач, фактическое время и блокеры в GitHub Issues/Projects.
- 1.2.3. [PM] Вести реестр рисков, оценивать вероятность и влияние (ЛР № 8).
- 1.2.4. [Вся команда] Сообщать о технических и командных рисках и предлагать меры.
- 1.2.5. [PM] Собирать плановые и фактические трудозатраты, рассчитывать EVM (ЛР № 9).
- 1.2.6. [Вся команда] Подтверждать процент готовности задач и затраченное время для EVM.
- 1.2.7. [PM] Оформлять Change Request и анализировать влияние изменений (ЛР № 14).
- 1.2.8. [Вся команда] Рассматривать Change Request на командном совете и фиксировать решение.
### 1.3. Завершение
- 1.3.1. [Вся команда] Провести ретроспективу Start–Stop–Continue и записать Lessons Learned.
- 1.3.2. [PM] Собрать артефакты и подготовить защиту проекта.
## 2. Организация инфраструктуры разработки и процессов DevOps
### 2.1. Репозиторий и рабочее окружение
- 2.1.1. [PM] Создать GitHub-репозиторий, выдать доступ участникам, добавить описание и README.
- 2.1.2. [Вся команда] Согласовать Git-flow: main, develop, feature/*, release/* и hotfix/*.
- 2.1.3. [Lead Dev] Настроить правила защиты main/develop, обязательный PR и проверку CI.
- 2.1.4. [Lead Dev] После выбора стека описать запуск проекта и при необходимости добавить Docker Compose.
- 2.1.5. [QA] Подготовить воспроизводимые тестовые данные и отдельную тестовую среду.
### 2.2. Сборка, проверка и доставка
- 2.2.1. [Lead Dev] Настроить сборку и линтер для выбранного стека в CI.
- 2.2.2. [Lead Dev / QA] Добавить запуск модульных и интеграционных тестов на PR.
- 2.2.3. [Lead Dev] Определить тестовый хостинг и автоматизировать CD после его выбора.
- 2.2.4. [QA] Проверять доступность тестового стенда и фиксировать сбои.
## 3. Аналитика и дизайн продукта
### 3.1. Требования и критерии
- 3.1.1. [Аналитик] Описать сценарии ввода ингредиентов, поиска и просмотра рецепта как User Stories.
- 3.1.2. [Аналитик / QA] Согласовать критерии приёмки, Definition of Done и граничные случаи.
- 3.1.3. [Аналитик] Определить правила сопоставления ингредиентов, единиц и замен.
### 3.2. Интерфейс
- 3.2.1. [Дизайнер] Подготовить макеты ввода продуктов, выдачи и карточки рецепта.
- 3.2.2. [Вся команда] Проверить макеты, доступность и техническую реализуемость.
## 4. Техническая разработка по функциональным модулям
### 4.1. Ввод ингредиентов и кухонный список
- 4.1.1. [Аналитик] Описать добавление, удаление, количество и нормализацию названий продуктов.
- 4.1.2. [Backend] Определить формат ингредиента и контракт передачи списка для поиска.
- 4.1.3. [Frontend / PM] Сверстать поле ввода и список выбранных ингредиентов по макету.
- 4.1.4. [Frontend] Связать ввод с поисковым запросом, обработать пустое и ошибочное состояние.
- 4.1.5. [QA] Подготовить позитивные и негативные тест-кейсы параллельно с разработкой.
- 4.1.6. [QA] Проверить модуль, завести баги в GitHub Issues и подтвердить исправления.
### 4.2. Каталог рецептов и данные
- 4.2.1. [Аналитик] Определить обязательные поля рецепта и критерии качества данных.
- 4.2.2. [Backend] Подготовить модель рецепта, ингредиентов, количества и шагов приготовления.
- 4.2.3. [Backend] Реализовать получение рецептов и подготовить небольшую проверяемую выборку.
- 4.2.4. [Frontend] Сверстать карточку рецепта и состояния загрузки по макету.
- 4.2.5. [Frontend] Интегрировать карточку с источником данных по согласованному контракту.
- 4.2.6. [QA] Составить тесты неполных данных и выполнить проверку с баг-репортами.
### 4.3. Подбор и ранжирование по имеющимся ингредиентам
- 4.3.1. [Аналитик] Зафиксировать правила «можно приготовить» и «не хватает продуктов».
- 4.3.2. [Backend] Реализовать сопоставление набора пользователя с составом рецептов.
- 4.3.3. [Backend] Добавить сортировку по числу недостающих продуктов и явный результат совпадения.
- 4.3.4. [Frontend] Сверстать выдачу и обозначения доступных/недостающих ингредиентов.
- 4.3.5. [Frontend] Интегрировать выдачу с поиском, показать отсутствие результатов и ошибки.
- 4.3.6. [QA] Подготовить тесты совпадений, количества, дублей и пустого ввода.
- 4.3.7. [QA] Проверить ранжирование, завести баги и подтвердить исправления.
### 4.4. Страница рецепта и список недостающих продуктов
- 4.4.1. [Аналитик] Описать сценарий просмотра рецепта и расчёт недостающих продуктов.
- 4.4.2. [Backend] Вернуть состав, шаги и недостающие ингредиенты в согласованном формате.
- 4.4.3. [Frontend] Сверстать страницу рецепта с шагами и перечнем недостающих продуктов.
- 4.4.4. [Frontend] Интегрировать страницу с данными и переходом из выдачи.
- 4.4.5. [QA] Подготовить тесты и проверить навигацию, полноту данных и крайние случаи.
- 4.4.6. [QA] Оформить дефекты и повторно проверить исправленные сценарии.
