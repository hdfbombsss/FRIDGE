Это рабочее распределение для старта. На первой командной встрече участники подтверждают навыки и доступное время; при перегрузке роли перераспределяются. PM записывает владельца каждой задачи в GitHub Issues и не берёт на себя сложную backend-архитектуру. По ИСР задачи `[Frontend / PM]` принадлежат Пешкову, остальные `[Frontend]` — Буглаку, `[Backend]` и `[Lead Dev]` — Сковородневу, `[Аналитик]`, `[QA]` и `[Дизайнер]` — Ярмову. Задачи `[Вся команда]` совместные.

## Параллельный конвейер модуля

1. Аналитик формулирует сценарий и критерии приёмки; QA сразу составляет тест-кейсы.
2. Backend согласует контракт данных; frontend начинает вёрстку с тестовыми данными.
3. Backend и frontend интегрируют части модуля; QA выполняет проверки на тестовом стенде.
4. Дефекты заводятся как Issues с шагами воспроизведения; исправление проверяется повторно.

Модуль завершён, когда сценарии и граничные случаи проверены, CI зелёный, PR прошёл ревью, дефекты блокирующего уровня закрыты и результат доступен на тестовом стенде.

## Управление задачами

GitHub Projects: `Backlog`, `Ready`, `In progress`, `Review`, `Done`. Каждая задача нижнего уровня ИСР — отдельный Issue с номером ИСР, результатом, критериями приёмки, владельцем, оценкой и ссылкой на PR. Метки: `pm`, `analysis`, `design`, `frontend`, `backend`, `qa`, `devops`, `bug`, а также `module:ingredients`, `module:catalog`, `module:matching`, `module:recipe`.

На короткой встрече участники сообщают результат, следующий шаг и блокеры. PM обновляет риски и план. Для EVM каждый фиксирует оценку, фактические затраты и подтверждённый процент готовности. Изменения границ проекта оформляются Change Request; решение команды записывается в Issue.

## Git-flow

`main` — проверенный релиз; `develop` — интеграция. Задачи идут в `feature/<issue>-<name>` от `develop`, исправления релиза — в `hotfix/<issue>-<name>` от `main`. Завершённые задачи попадают через PR и ревью. Для выпуска создаётся `release/<version>`, после проверки изменения попадают в `main` и обратно в `develop`. Прямые push в защищённые ветки и force push запрещаются правилами репозитория.

## Риски первого этапа

| Риск | Ранний сигнал | Действие |
|---|---|---|
| Перегрузка backend или QA | задачи задерживаются у одного исполнителя | пересмотреть объём и перераспределить задачи на встрече |
| Нет пригодных рецептов | нет данных для демонстрации | собрать малую проверенную выборку с разрешённым использованием |
| Зависимость от внешнего API | лимиты или ошибки сервиса | сохранить локальную выборку и изолировать источник данных |
| Интеграция задерживается | frontend/backend расходятся по формату | согласовать контракт до кодинга и тестировать на одном примере |
